# 专家评审 Rubric（简历草稿打分）

生成简历后，扮演资深简历专家用本 rubric **逐条**评审，给出分数 + 可执行的改进建议，写入匹配报告的「专家评审」段。目的是把"差不多能用"逼向"专家水准"。

## 六个维度（每项 1~5 分）

| 维度 | 1 分（差） | 5 分（优） |
|---|---|---|
| **岗位主线 Role Focus** (`role_focus`) | 看不出候选人与岗位使命的关系，内容平均用力 | Top 3 核心要求有明确证据，最强证据优先且弱相关内容克制 |
| **证据强度 Evidence** (`evidence`) | 多为自我评价、职责或技术名，读不出解决了什么问题 | 核心结论以问题—方法—结果组织，方法对应真实约束，结果可验证且不强求每条都有数字 |
| **个人贡献 Ownership** (`ownership`) | 团队成果与个人工作混在一起，职责边界不清 | 能看出本人负责范围、关键决策和交付边界，不冒领团队成果 |
| **可信度 Credibility** (`credibility`) | 指标无对象/口径，Demo 包装成生产系统，或把 Prompt 约束写成运行时保证 | 正文保留指标对象与基线/结果，完整样本和评测方式在审计中可追溯；约束层级和成熟度准确，措辞经得起追问 |
| **影响力 Impact** (`impact`) | 只写过程，没有结果或实际价值 | 关键工作有明确交付、效果或业务/工程价值，不强求每条都有数字 |
| **清晰度 Clarity** (`clarity`) | 冗长、组件清单化、术语堆砌，难以快速扫读 | 句子精炼、层次清楚，一条只承载一个核心判断 |

## ATS 与页面独立检查（不计入 30 分）

- **ATS**：读取 `ats_check.py` 的关键词命中结果，报告缺失与异常；不得通过重复堆词给内容评分加分。
- **页面**：读取 `page_metrics.py` 的页数和填充率。目标页数是交付约束；填充率只报告稀疏/拥挤提示，不影响上述六维得分。
- **视觉**：核对公司法定主体与集团/品牌旁注、整体加粗、长公司名和日期间距、重叠/截断及论文标题换行；视觉问题归入 clarity 的 actionable 建议，但不改写客观字段。

## 评分与处置（喂给 SPEC §11 的三态裁决，不再是"禁止交付"的硬停）

这些阈值**不再表示"达不到就不许交付"**，而是作为 `scripts/polish_gate.py` 的输入，由它按 SPEC §11.7/§11.8 决定**交付哪一版 + 是否标可投递**。冲突时以 §11 为准。

- **总分 ≥ 26/30（`DELIVER_SCORE`）且无维度 ≤2、页数符合目标、无 high red_flag** → `pass`，正常交付。
- **达不到 26 但 ≥ 24（`SOFT_FLOOR`）、无 high red_flag、页数符合目标** → 当前已评审版仍可**正常交付**（`deliverable=true`）；< 24 或仍有 high red_flag → 只能标为 `NOT-READY`（`resume.DRAFT.pdf`），不静默当成品。
- **任一维度 ≤2**：归类为改进点喂给 gate。属 `actionable`（措辞/排序/删冗余/降低过度包装等）才可能触发**至多一轮**迭代；属 `needs-fact`（缺指标定义、ownership 证据或 JD 能力事实）则触发缺口追问访谈，**不消耗迭代轮次、绝不编造**。

## 输出格式（写入 match-report.md 的「专家评审」段）

```markdown
## 专家评审（满分 30）

| 维度 | 分 | 说明与改进建议 |
|---|---|---|
| 岗位主线 | 4 | Agent 工作流证据已前置，但开发工具场景仍不够突出 |
| 证据强度 | 4 | expe-1-b2 有动作和方案，实际交付状态可更明确 |
| 个人贡献 | 3 | proj-agent 没有区分本人实现与团队已有能力 |
| 可信度 | 3 | `Top1 81.34%` 缺指标口径、基线与评测方式 |
| 影响力 | 4 | 核心经历有结果，个别 bullet 仍偏过程 |
| 清晰度 | 4 | 一条句子堆叠多个组件，建议保留关键技术选择 |
| **合计** | **22/30** | 先修可信度和 ownership，再由 gate 裁决 |

### 独立检查
- ATS：核心关键词命中；不因重复出现而加分。
- 页面：1 页；填充率偏高，提示检查可读性。

### 逐条改进清单
- [ ] expe-1-b2：补充 `Top1 81.34%` 的口径、基线和评测方式；若无法确认则删除该数字
- [ ] proj-agent-b1：明确本人负责的模块，避免把 Demo 包装成已上线的生产系统
- ...
```

## 评审原则

- 改进建议必须**可执行**（指出具体 bullet + 怎么改），不空泛。
- 核心 bullet 缺少问题、方法或结果时，指出缺失环节；不要要求机械添加三个标签，也不要把每条都改成同一种「针对……」句式。
- 调参过程、权重和超参数只有在解释关键技术决策时才保留；若结果指标已经足够，建议移出简历而不是继续堆数字。
- 凡是建议补指标定义、ownership 或成果的，**只能向用户追问真实信息**，绝不替用户编造（见 tailoring-rules.md）。
- 评审不得建议改写 A1 中的 verbatim 字段（公司/岗位/时间/论文名/项目名）。
